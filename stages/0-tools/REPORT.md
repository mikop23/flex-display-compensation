# 0단계 REPORT — 기초 도구

## 문제
이후 단계(기하 왜곡·휘도 보정)를 직접 구현하려면 "이미지 = 행렬"로 다루는 도구가 먼저 필요하다.
목표: 파이썬 환경을 갖추고, 밝기·대비·휘도를 행렬 연산으로 직접 다룰 수 있게 되기.

## 방법
- 환경: Windows, Python 3.12, venv, numpy / opencv-python / pillow / matplotlib / jupyter
  - `check_env.py`: 라이브러리 버전 확인 + 테스트 이미지 표시
- `numpy_basics.py`
  - 인덱싱 `img[y, x]` (행 = 세로), 브로드캐스팅, reshape
  - 밝기: `img + 50`
  - 대비: `k × (x − 128) + 128` (128 기준으로 거리를 k배)
  - 결과를 `np.clip(0, 255)`로 클리핑해서 8비트 범위 유지
- `luminance_heatmap.py`
  - OpenCV로 읽기 → BGR 채널 분리 (RGB 순서 아님 주의)
  - 휘도 Y = 0.299R + 0.587G + 0.114B (눈이 밝게 느끼는 G에 가중치)
  - 컬러맵 inferno + colorbar (jet은 가짜 경계가 보여서 제외)

## 한계
- 밝기를 올리면 255 근처가 포화(클리핑)돼서 서로 다른 값이 같은 값이 된다 → 잘린 정보는 SW로 복원 불가
  - HW 후보: 휘도 여유(헤드룸), 소자 효율
- 선형 대비 늘이기는 양 끝을 잘라 계조가 손실된다 → 비선형(S-curve)으로 완화는 되지만 8비트 계조 수 한계는 남음
  - HW 후보: HDR, 높은 비트 깊이 구동
- 0.299/0.587/0.114 가중치는 sRGB 계열 가정이라 실제 패널 휘도(cd/m²)와 다르다 → 2단계 측광에서 다시 다룸

## 회고
- 제일 크게 이해한 것: 이미지가 결국 숫자 행렬이라 밝기·대비가 덧셈·곱셈 한 줄이라는 것. 그리고 연산 결과가 0~255를 넘으면 잘려서 정보가 사라진다는 것이 보정의 첫 번째 한계라는 것.
- 몰입이 잘 된 순간: 대비 공식이 왜 그런지 따지다가 거리 기반 비선형 대비를 직접 떠올렸을 때 (실제로 쓰이는 S-curve 방식이었음).
- 몰입이 안 된 순간: 환경 세팅 문제(PowerShell 실행 정책, .gitignore 위치, requirements.txt 인코딩, 자동저장 꺼짐)로 코드 전에 시간이 많이 들었을 때.
